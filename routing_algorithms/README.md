The aim of this thesis is to implement Dijkstra and A* on Barcelona's subway network. After the
`data_validation` pipeline produces [`data/6_weights/weights.txt`](../data/6_weights/weights.txt),
that file is the real, GTFS-derived weighted graph the algorithms run on.

## algorithms_utils.py

Graph types (`Graph`, `Node`, `NodeFmt`), the `MinHeap` priority queue, path reconstruction
(`rebuild_path`), and print/display helpers shared by both `dijkstra/` and `a_star/`. Nothing
here is specific to either algorithm or to the comparison reports below (see `reports/`).

## dijkstra/

- `dijkstra.py`: the main file. Builds the graph straight from `weights.txt` and runs Dijkstra on
  it.
- `dijkstra_utils.py`: `dijkstra` and `cut_dijkstra`, built on top of `algorithms_utils.py`.
- `dijkstra_example.py`: small toy graphs meant to leave an understandable, traceable example of
  how the algorithm works, separate from the real subway data.
- `resources/`: images for the four examples in `dijkstra_example.py` and the `.txt` traces
  generated by `dijkstra.py`.

## a_star/

- `a_star.py`: the main file, mirroring `dijkstra.py` but for A*.
- `a_star_utils.py`: the `a_star` algorithm plus the geographic heuristic (straight-line
  distance / v_max), built on top of `algorithms_utils.py`.
- `a_star_example.py`: a small toy graph with a hardcoded heuristic, separate from the real
  subway data.
- `resources/`: `.txt` traces generated by `a_star.py`.

## reports/

Platform-to-platform comparison reports, kept separate from the algorithm implementations they
call since each report depends on the other's output for its analysis:

- `report_utils.py`: shared reporting machinery (`ReportRow`, `compute_report_row`,
  `run_platform_pair_report`, etc.), used by both reports below.
- `paths.py`: `REPORTS_BASE` and the `DIJKSTRA_REPORT_FILE`/`A_STAR_REPORT_FILE` output paths,
  mirroring `data_validation/gtfs_utils.py`'s constants section, so the two reports and
  `scripts/from_txt_to_xlsx.py` share one source of truth instead of each recomputing the path.
- `a_star_need_report.py`: runs `cut_dijkstra` over every directed platform pair to measure, via
  `proportion = path_vertices / cut_iterations`, where a heuristic could help. Writes
  `DIJKSTRA_REPORT_FILE`.
- `a_star_report.py`: reruns the same pairs with A* and the real geographic heuristic, so its
  `proportion` can be compared side-by-side against `dijkstra_report.txt` to see how much of that
  theoretical opportunity the heuristic actually captures. Writes `A_STAR_REPORT_FILE`.
- `resources/`: `dijkstra_report.txt` and `a_star_report.txt`, the two outputs above, kept
  together so their `proportion` columns are easy to compare side-by-side (e.g. via
  `scripts/from_txt_to_xlsx.py`).
